Durable AI and business workflows in Kotlin

Put model calls, business rules and human approval into one workflow, with rate limits, retries, fallbacks and dead letters you can replay. Run it without an engine, or compile it to BPMN for Camunda 7, CIB seven and Camunda 8.

What a step with a model call gets

Each need is one line in the workflow, the same on every backend.

Stay within the provider's request limits
rateLimit = perSecond(5) on the task, or one limit for the whole run.
Try again after a busy response or a timeout
retry = RetryPolicy(maxAttempts = 5) with backoff, and timeout = 30.seconds.
Send uncertain results to a person
.catching<LowConfidence> { } for a branch, userTask(...) for an approval with form data.
Wait for a batch job or a webhook, with a deadline
awaitMessage("batch-done", timeout = 2.hours) { item, data -> } with onTimeout { }.
Work through thousands of documents
fanOut(expand, concurrency = 16) { }, folded back with reduce.
Undo side effects when an item gives up
compensate { } runs in reverse order of the completed steps.
Look at failed items and run them again
A dead-letter store, backend.requeue and the web console.
See latency and outcomes per step
Metrics per task through Micrometer or OpenTelemetry, and one span per task.

Install & run

loadshift is built with the Kotlin Toolchain. Clone it, build it, and run the demo workflow without an engine.

./kotlin test
./kotlin run -m loadshift-demo

Work items

A work item is the unit that travels through a workflow. Implement WorkItem with a @Serializable data class; fields are plain constructor properties. The Camunda backends use kotlinx.serialization to convert them to and from process variables. Override key to give items a stable identity for tracing and dead letters.

WorkItems.kt
@Serializable
data class Customer(var id: String, var attempts: Int = 0) : WorkItem {
    override val key get() = id
}

@Serializable
data class Contact(var id: String, var email: String? = null) : WorkItem {
    override val key get() = id
}

val vip = Customer("cust-1")

@Serializable is required on any work item type used as a workflow input or fanOut child when running on a Camunda backend. The local backend passes objects in memory and calls the codec only when RunConfig.deadLetters is set.

Workflows & tasks

A workflow is a named sequence of steps over one work-item type. input(...) seeds it with a fixed list and task declares a unit of work under a topic name.

Basics.kt
val onboarding = workflow<Customer>("onboarding") {
    input(customers)

    task("validate") { println("validating ${it.id}") }
    task("provision") { provision(it) }
    task("welcome-mail") { sendWelcome(it) }
}

On an engine, a task's topic becomes the job type <workflow-key>/<topic>. Topics must be unique within a workflow. The workflow key is the lowercased name with every character other than letters, digits, _ and - replaced by -; it must start with a letter or _.

Branching & loops

Control flow is part of the definition, not buried in task bodies, so it compiles to real BPMN gateways. condition / otherwise branches, loop repeats while a guard holds, parallel runs branches concurrently.

Branching.kt
condition({ it.email == null }) {
    task("flag-missing") { flag(it) }
} otherwise {
    task("cleanup") { clean(it) }
}

loop({ it.attempts < 3 }) {
    task("poll-status") { it.attempts = it.attempts + 1 }
}

parallel {
    branch { task("index") { index(it) } }
    branch { task("notify") { notify(it) } }
}

wait(15.minutes)
task("settle") { settle(it) }

timeout(10.minutes) {
    task("call-vendor") { callVendor(it) }
}

awaitMessage("payment-confirmed")
task("fulfil") { fulfil(it) }

A loop that exceeds RunConfig(maxLoopIterations = …) dead-letters the item. wait pauses the item for a fixed duration: a timer catch event on an engine, a suspending delay in-process. timeout cancels its block when the duration passes and dead-letters the item; on an engine the block is an embedded subprocess with an interrupting boundary timer.

awaitSignal(name) parks an item until backend.signal(name), which releases every item waiting for that signal at that moment, across all workflows of the backend; on an engine it compiles to a signal catch event.

userTask("approve", assignee = "ops") { item, form -> } waits for a person: backend.userTasks(workflow) lists the open tasks and backend.completeUserTask(id, form) completes one, after which the block applies the form to the item. On an engine it is the engine's own user task.

call(workflow) runs another workflow with the same item type on the item and continues with the item as the called steps left it. A dead letter inside the called steps is recorded under the called workflow and the caller continues. On an engine the called workflow is deployed with the caller and started through a call activity.

awaitMessage parks an item until an event arrives. The run handle delivers it with send(message, key) to the item with that key, or with broadcast(message) to every waiting item, including items that reach the wait later. A send that arrives before the item waits is delivered once it does. On an engine both reach waiting instances of the same workflow, whichever run started them. Camunda 8 correlates on the key <workflow-key>:<item-key>; Camunda 7 and CIB seven correlate on the variables loadshiftWorkflow and loadshiftKey.

Messages.kt
awaitMessage("payment-confirmed", timeout = 3.days) { order, data ->
    order.paidAmount = data.getValue("amount").jsonPrimitive.double
} onTimeout {
    task("send-reminder") { remind(it) }
}
task("fulfil") { fulfil(it) }

handle.send("payment-confirmed", "order-17", buildJsonObject { put("amount", 99.5) })

send(message, key, data) and broadcast(message, data) carry a JSON object that the block of awaitMessage applies to the item. With timeout, an item whose message does not arrive in time runs the onTimeout steps instead; both paths continue with the next step. On an engine the block is a service task after the message catch event, and timeout compiles to an event-based gateway that races the message against a timer.

Saga.kt
task("charge") { charge(it) } compensate { refund(it) }
task("reserve") { reserve(it) } compensate { release(it) }
task("ship") { ship(it) }

When ship dead-letters the item, release runs first and refund second: compensations run in reverse order of the completed steps. A compensation that throws adds a dead letter with the topic compensate_<topic>. On an engine, the worker adds a snapshot of the item to the process variable loadshiftCompensation_<topic> each time the step completes, so the worker that dead-letters the item runs the compensation even when another worker ran the step, once for every run of a step inside a loop.

Catching.kt
task("reserve") { reserve(it) }
    .catching<OutOfStock> { task("backorder") { backorder(it) } }
task("ship") { ship(it) }

When reserve throws an OutOfStock, the item runs the backorder branch without further attempts and then continues with ship. Other exceptions follow the retry policy and RunConfig.onError. On an engine the branch starts at an error boundary event on the service task.

Fan-out

Expand one parent item into many children and process them with bounded concurrency. The child block is a full workflow scope: tasks, branching, even nested fan-out. On Camunda each fan-out level becomes its own process, invoked as a call activity.

FanOut.kt
val cleanup = workflow<Customer>("contact-cleanup") {
    input(customers)

    fanOut(expand = { fetchContacts(it.id) }, concurrency = 4) {
        condition({ it.email == null }) {
            task("flag-missing") { flag(it) }
        } otherwise {
            task("scrub") { scrub(it) }
        }
    }
}

Tasks inside a fan-out can read a parent-derived value through context(). Opt in by passing a context transform; without it context() is null. Pass context = { it } to expose the parent item itself.

ParentAccess.kt
fanOut(
    expand = { customer -> fetchOrders(customer.id) },
    context = { customer -> customer.address },
) {
    task("ship") { order ->
        ship(order, context())
    }
}

context() resolves against the level it is called in and exposes the nearest parent. To reach further up, a nested fanOut receives the enclosing context value as a second argument, so you fold the chain into your own value as you descend. Use the built-in Parent(item, parent) carrier to keep both levels without declaring a type, or compose your own.

CumulativeContext.kt
fanOut(
    expand = { customer -> fetchOrders(customer.id) },
    context = { customer -> customer },
) {
    fanOut(
        expand = { order -> order.lines },
        context = { order, customer -> Parent(order, customer) },
    ) {
        task("ship") { line ->
            val (order, customer) = context()
            ship(line, order, customer)
        }
    }
}

To aggregate children back into the parent, chain a terminal onto fanOut. join() just waits for every child; collect gathers the finished children into a list; reduce folds them through initial/combine into one aggregate (streaming, so it never materializes the children). Each runs its callback on the parent once the fan joins.

FanReduce.kt
fanOut(expand = { customer -> fetchOrders(customer.id) }, concurrency = 8) {
    task("charge") { order -> charge(order) }
}.reduce(0.0, combine = { sum, order -> sum + order.amount }) { customer, total ->
    customer.billed = total
}

reduce and collect fold over the children as produced by expand — identically on the local and Camunda backends. The child body runs per child for its side effects; aggregate the values you need from the expanded items rather than from in-task mutations.

Streaming sources

For workloads too big for a list, seed from a Flow or from a paginated API. paginate walks a cursor until it returns null; items stream through the workflow without ever materializing the full set.

Sources.kt
val allCustomers = paginate { cursor ->
    val page = crm.customers(after = cursor)
    Page(page.items, page.nextCursor)
}

val sync = workflow<Customer>("sync-all") {
    input(allCustomers)
    task("sync") { push(it) }
}

Fan-out can paginate per parent too, with paginateWith:

PaginatedFanOut.kt
fanOut(
    paginateWith { customer, cursor -> crm.contacts(customer.id, cursor) },
    concurrency = 8,
) {
    task("scrub") { scrub(it) }
}

Reliability

Every task takes retry, timeout and rateLimit directly. Retries back off exponentially with jitter; rate limits are enforced per topic.

Reliability.kt
task(
    "enrich",
    retry = RetryPolicy(maxAttempts = 5, baseDelay = 200.milliseconds),
    timeout = 10.seconds,
    rateLimit = perSecond(50),
) { enrich(it) }

A task's retry policy applies wherever it runs, including inside a parallel branch: a failing branch task is retried in full (e.g. all 3 attempts of the default policy) before the item is handed to the run's ErrorPolicy.

What happens when a task still fails is a run-level decision, set with RunConfig.onError.

ErrorPolicy.kt
val result = LocalBackend().run(
    cleanup,
    RunConfig(
        maxConcurrency = 32,
        retry = RetryPolicy(maxAttempts = 3),
        onError = ErrorPolicy.DeadLetter,
    ),
).await()

result.deadLetters.forEach { println("${it.topic}: ${it.error}") }
POLICYITEMCOMPENSATIONSCOUNTED AS
DeadLetterEnds; its parent continuesRun in reverse orderA dead letter
SkipEnds; its parent continuesNot runskipped
FailThe run fails and its other items are cancelledNot runfailed

Dead letters can be kept and run again. With RunConfig.deadLetters every dead letter is stored together with the item and its workflow level; backend.requeue runs the stored items again from the start of their level.

Requeue.kt
val store = SqliteDeadLetterStore("dead-letters.db")
backend.run(cleanup, RunConfig(deadLetters = store)).await()

val page = store.list(cleanup.key, limit = 100)
backend.requeue(cleanup, page.records, RunConfig(deadLetters = store)).await()

A requeued fan-out child runs the child's steps with its parents available through context(); its parent's reduce or collect does not run again. A record is removed once its item has started, and an item that fails again is recorded again. The web console lists the records of the workflows passed to DeadLetterConsole and requeues or discards them.

On an engine, task bodies run at least once: the engine delivers a job again when the worker stops before completing it or when the job's lock expires. Write task bodies so that running them twice has the same effect as running them once. While a body runs, the worker extends the job's lock every third of RunConfig.lockDuration. A worker runs a job at most once at a time: when the engine hands the same job to it again while the body is still running, the worker skips the second copy.

Backends

The definition is backend-agnostic. LocalBackend interprets it in-process. Camunda7Backend, for Camunda 7 and CIB seven, and Camunda8Backend compile the same definition to BPMN, deploy it, start one process instance per item and work the jobs with your Kotlin task bodies. Camunda 7 to Camunda 8 shows what the BPMN contains for each engine and how to switch a workflow over.

Backends.kt
LocalBackend().dryRun(cleanup).forEach(::println)

LocalBackend().run(cleanup).await()

Camunda7Backend(
    "http://localhost:8080/engine-rest",
    credentials = BasicCredentials("demo", "demo"),
).run(cleanup).await()

Camunda8Backend(
    "https://camunda.example.com",
    auth = Camunda8Auth.ClientCredentials(tokenUrl, clientId, clientSecret, audience = "zeebe-api"),
).run(cleanup).await()

LocalBackend.dryRun walks the plan without executing task bodies and returns the topics in visit order. On an engine, RunConfig(dryRun = true) compiles the BPMN and deploys and starts nothing. RunConfig(maxInFlight = n) keeps at most n root process instances of a run unfinished; seeding waits until one finishes. tenantId on Camunda7Backend and Camunda8Backend deploys, starts, works and correlates within one tenant. version("2") in a workflow sets the version tag of its processes, and backend.migrate(workflow) deploys it and moves active instances of older definitions to it, matching elements by id.

Handover.kt
val handle = Camunda8Backend(base).run(cleanup)
handle.detach()

val takeover = Camunda8Backend(base).attach(cleanup)
takeover.await()

detach() stops seeding and fetching, waits for running task bodies and leaves the process instances on the engine. attach(workflow) works the active instances of the workflow, including instances that appear while it runs, and finishes when none are left.

Run control

run() returns a RunHandle with progress counters, pause, resume, cancel, detach and an awaitable result. RunConfig.start picks one of Start.Now, Start.Manual, Start.At or Start.Cron.

RunControl.kt
val handle = LocalBackend().run(sync, RunConfig(start = Start.Manual))

handle.start()
println(handle.progress())

handle.pause()
handle.resume()

val result = handle.await()
println("done=${result.done} failed=${result.failed} skipped=${result.skipped}")
Items.kt
println(handle.item("order-17"))
handle.cancelItem("order-18")

backend.requeue(sync, store.forKey(sync.key, "order-19"), RunConfig(deadLetters = store))

While a run is paused, tasks that have not started wait and running task bodies finish. cancel() stops the run and, on an engine, cancels its process instances. item(key) reports the state, current topic and dead letters of one top-level item. cancelItem(key) stops that item without running its compensations and counts it as cancelled; on an engine, its root process instance is cancelled. Start.Manual waits for handle.start(). loadshift-web's ControlServer offers the same controls over HTTP: POST /api/runs/{id}/start, /pause, /resume, /cancel and /detach, plus GET /api/runs/{id}/items/{key} and POST /api/runs/{id}/items/{key}/cancel. With ControlServer(backend, logs = sink, deadLetters = console) the dashboard shows each run's log entries and dead-letter records with their items. The console signs users in with HTTP basic authentication (ConsoleCredentials) or through an OpenID Connect provider (ConsoleOidc), which also lets API clients call it with the provider's bearer tokens.

ScheduledStart.kt
LocalBackend().run(sync, RunConfig(start = Start.At(Clock.System.now() + 5.minutes)))

LocalBackend().run(sync, RunConfig(start = Start.Cron("0 9 * * MON-FRI", TimeZone.of("Europe/Berlin"))))

Start.At seeds once at the given instant. Start.Cron takes a five-field expression (minute, hour, day of month, month, day of week) evaluated in the given zone, the system zone by default. Fields accept *, ?, lists, ranges, steps such as */15 or 5/20, and the names JAN–DEC and SUN–SAT. When day of month and day of week are both restricted, a day matches if either field matches. On every tick the run seeds input() again and runs that batch to completion before it waits for the next tick. An invalid expression throws IllegalArgumentException when Start.Cron is created.

On Camunda 7, CIB seven and Camunda 8 the schedule lives on the engine: the run deploys the process <workflow-key>_loadshift_schedule, whose timer waits for the next tick. A tick that passes while no worker runs is seeded once a worker with Start.Cron runs again, and items whose root instance is still active are skipped. cancel() ends the schedule; detach() leaves it on the engine.

Logging

Task bodies can call log() to record structured entries that carry the execution tree context: run id, workflow name, the ancestor item-key path through nested fanOuts, the current item key, and the current task's topic.

Logging.kt
task("charge") { order ->
    log("charging customer", "orderId" to order.id, "amount" to order.amount)
}

Logging is opt-in via RunConfig.logSink (default NoopLogSink, which discards everything). loadshift-sqlite provides SqliteLogSink, which persists entries to a SQLite database.

SqliteLog.kt
val sink = SqliteLogSink("logs.db")
backend.run(workflow, RunConfig(logSink = sink)).await()
